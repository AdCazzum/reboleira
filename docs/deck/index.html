The problem

The web ships one interface and hopes it fits everybody.

  • It doesn't fit. Roughly one adult in ten reads with dyslexia. Many more have low vision, limited attention, or are simply reading in their second language.
  • Accessibility settings are per-site. Every site you use asks you to configure it again — if it offers anything at all. Most offer nothing.
  • Nobody wants to declare a disability to 400 websites. The moment your needs live in someone else's user database, you've handed over sensitive information for a font size.
The fix people actually want: say once how you read, and have every page respect it — without that statement becoming a record on somebody's server.

An extension that regenerates the page for you.

The part that makes it safe to ship

The AI may rewrite the words. It can never invent where a click goes.

This is the difference between a demo and something you'd let a bank customer use.

  • Every link and button is the real one. The regenerated interface points back at the actual elements of the original page; clicking "Add to cart" fires the site's own button.
  • Made-up destinations are rejected, not trusted. If the AI invents a link with no counterpart on the page, the result is thrown away before anything is drawn — a check in code, not a polite instruction in a prompt.
  • The original page is never modified. The adapted view is drawn in a sealed layer on top and removed when you toggle back.
Why it matters commercially: a personalisation layer that can hallucinate a checkout link is unshippable. Ours structurally cannot — the worst case is that a block is dropped, never that a click goes somewhere the page never offered.

Where the profile lives

Nobody holds your profile. Not even us.

This is the whole journey of a profile — and it is also the answer to "what did each partner actually do".

1

You fill in a form

How you read. It never leaves the browser as plain text.

2

Your wallet locks it

A signature from your wallet derives the encryption key. Only you can unlock it.

3

0G stores the sealed file

The encrypted profile goes to 0G Storage. What's stored is unreadable without your signature.

4

ENS points at it

Your own name — reboleira.eth — carries a pointer to the file and a flag that a real human is behind it.

5

0G Compute builds the page

Profile plus page content go into a sealed environment. Out comes your interface.

There is no Reboleira account, no Reboleira database and no Reboleira server in this picture. If we disappeared tomorrow, the profile would still be yours and still readable by anything that knows how to look.

Partners — the honest test

Take one out and the product stops working.

The useful question about any integration is not "did you call their API". It's "what breaks without it". Here is our answer for each.

Remove……and this is what happensCould we have faked it?
ENS We'd need our own user database to know whose profile is whose. The profile stops being the person's and starts being ours — the exact thing the pitch is against. Only by becoming a normal SaaS with logins.
0G Storage The encrypted profile has to sit on a server somebody operates. Availability and takedown become our problem, and the user's. Yes — and it would have made the privacy claim untrue.
0G Compute The page content and someone's accessibility needs would be posted to a commercial AI API. That's the most sensitive combination in the product, handed to a third party. Yes — this is the shortcut we deliberately didn't take.
World ID "One person, one profile" becomes an honour-system claim. Anyone can mint a thousand names and a thousand "accessibility" profiles. No, not credibly.

Each partner sits on the critical path of a different guarantee: ENS on ownership, 0G on privacy, World ID on uniqueness. None of them is a logo on a slide.

The one gap we won't hide

Reading from 0G inside the page

0G's storage library can only download from a server environment, not from inside a web page yet. So the wizard does the real upload and the real ENS write; the extension currently reads the profile through its local copy.

Known limitation
And the demo cannot go blank. Every live step has a pre-computed fallback: bad venue wifi, a declined signature or a network outage all drop silently to a stored result instead of a broken page. Which path was used is logged, so a fallback can never be passed off as a live run.

What's next

Today the page adapts to what you declared. Next, to how you actually read.

  • A profile that learns. If someone always skips the video and enlarges the text, the profile should notice — without that behaviour leaving their device. Deliberately out of scope for this build.
  • Read the profile straight from 0G in the browser, closing the one gap on the status slide.
  • Profiles that travel. The same ENS-published profile could be read by a native app, an operating system, or a site that wants to serve it directly — nothing about it is extension-specific.
The one-line version: we made accessibility something a person carries with them, instead of something every website has to remember to offer.
